Git & GitHub, explained for
data pipelines.

Version control isn't just for software engineers. As data engineers, we version pipelines, schemas, and configs the same way — and GitHub is where that history lives, gets reviewed, and gets deployed.

01 — Foundations

Why GitHub matters in data engineering

// 01

Version history

Every change to a pipeline, DAG, or SQL model is tracked. If a transformation breaks prod, you can see exactly what changed and revert it in seconds.

// 02

Code review

Pull requests let a teammate review your schema migration or Airflow DAG before it touches production data — catching mistakes before they cost you.

// 03

CI/CD pipelines

GitHub Actions can automatically test your dbt models, lint SQL, or deploy a Spark job the moment code is merged — no manual steps, no "it works on my machine."

// 04

Collaboration at scale

Multiple engineers can work on the same warehouse repo simultaneously using branches, without overwriting each other's work.

02 — Git Tags

What tags are, and why we use them

A tag is a permanent pointer to one specific commit — usually one that marks a release. Unlike a branch, a tag doesn't move as new commits come in. Think of it as a bookmark stuck to one exact point in history.

Why tags matter for a data pipeline

  • Mark exactly which pipeline version produced last quarter's report — so results are reproducible.
  • Roll back a broken deployment to a known-good release instantly (v1.4.0 instead of guessing a commit hash).
  • Pin a dependency: "our warehouse schema uses tag schema-v3," so nothing downstream breaks silently.
  • Give non-engineers (analysts, stakeholders) a clean version number instead of a 40-character commit hash.
terminalbash
# create a lightweight tag on the current commit
git tag v1.0.0

# create an annotated tag (recommended — stores author, date, message)
git tag -a v1.0.0 -m "first stable ETL release"

# push a single tag to GitHub
git push origin v1.0.0

# push ALL local tags to GitHub
git push origin --tags

# see all tags in the repo
git tag

# check out the exact code from a tagged release
git checkout v1.0.0

Common tag naming patterns you'll see

v1.0.0, v1.1.0, v2.0.0
Semantic versioning — major.minor.patch. Patch = bug fix, minor = new feature (backwards compatible), major = breaking change.
schema-v3
Marks a specific version of a database schema — useful when a table structure changes and downstream jobs depend on knowing which version they're reading.
release-2026-08-20
Date-based tags, common in pipelines that deploy on a schedule rather than by feature.
rc1, rc2 (release candidate)
Marks a build that's being tested before it's promoted to a full release tag.

Lightweight vs. annotated: a lightweight tag is just a name pointing at a commit. An annotated tag (-a) is a full object with its own author, date, and message — use annotated tags for anything you'd call a "release."

03 — Applied workflow

A typical data engineering Git workflow

Branch off main

git checkout -b feature/add-customer-dim — build your new dbt model or DAG in isolation, without touching the pipeline everyone else depends on.

Commit in small, logical steps

git commit -m "add customer dimension table" — small commits make it easy to find exactly where a bug was introduced later.

Open a pull request

Push your branch and open a PR on GitHub. A teammate reviews the SQL/DAG logic before it merges into main.

CI runs automatically

GitHub Actions lints your code, runs dbt tests, and checks the pipeline builds — before a human even has to look.

Merge and tag the release

Once merged, tag the commit (git tag -a v1.2.0) so this exact pipeline version can always be reproduced or rolled back to.
